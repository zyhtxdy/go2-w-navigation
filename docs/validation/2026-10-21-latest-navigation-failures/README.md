### 支撑问题的范围

本轮全局支撑来自固定 `/offline_map/support`。下载的 NX 地图与本机 `maps/lab_v1_navigation` 的支撑文件及元数据 SHA-256 相同，共 891 个导出支撑点。

`support_nearest.json` 将日志中保留三位小数的失败坐标与固定地图作最近邻比对：多处最近支撑约相距 0.16～0.22 m，高度差很小。例如 `(2.619,-0.281,-0.390)` 最近支撑为 `(2.8,-0.4,-0.389981)`，水平距离约 0.217 m。

实际代码分别检查“支撑格点之间是否能连接”和“路径沿途每个经过的网格是否有支撑”。离线入口将前者 `surface_connection_radius` 按 0.20 m 地图间距调整到约 0.30 m，后者仍使用独立的 `support_radius=0.15 m`，在 0.10 m 网格上向上取整为 2 格搜索。不同坐标落入的网格也会影响覆盖。因此，前一项改进不保证后一项全部通过；这些日志不足以证明真实地面有坡道或缺口。

### 障碍问题的范围

本轮 90 条外廓碰撞诊断均标记实时输入 `/terrain/obstacles_global`，其中 64 条为 `measured_return`、26 条为 `synthetic_terrain_marker`；另有 4 条不连通诊断涉及合成标记。诊断次数不是独立障碍物数量。

已证实实时障碍输入参与了失败。仅凭体素位置与分类，不能判断实测点对应挡板、行人、机身、自反射还是配准误差，也不能把合成标记一律称为误报。需要取消前后的原始点云、位姿与分类结果才能核实。

## 控制计算与后续顺序

控制器日志出现 1033 条未达到配置 20 Hz 的告警，说明本轮控制计算/调度余量不足；告警条数不能换算成实际控制频率或独立失败次数。本轮没有记录控制器报 `Failed to make progress` 等直接控制失败；上表 6 次失败都能对上规划拒绝。

建议按以下顺序处理：

1. 在本机用固定地图复现近起点连续支撑拒绝，使起点连接、搜索边与最终路径检查的支撑规则一致；保留真实缺口、高差和碰撞检查。
2. 核对实时障碍与静态地图对齐、真实物体和机身过滤；同时检查目标原地转向的矩形扫掠，不能只看目标 XY。
3. 为后台全局校验超时增加当时输入年龄、候选质量和耗时记录，确定原因后再优化；不直接取消保护。
4. 在允许修改两台机器时间配置时统一时钟；重新检查 RViz 的 TF 丢帧。时钟管理属于 NX 宿主机范围，本次未操作。
5. 单独测量控制周期和 CPU 开销，再决定是否降低 MPPI 采样量或调整控制频率。
