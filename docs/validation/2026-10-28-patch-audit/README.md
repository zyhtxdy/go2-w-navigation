# 2026-10-28 近期导航补丁复核

结论：近期修改确实存在已确认的回归和未充分验证就默认启用的行为变化。不能用单元测试全部通过，代替真实首次启动、冻结地图上的新旧路径比较和机器人执行验证。本轮只读取本机源码、已保存的 NX 日志及地图，并查询上游资料；没有连接 NX，没有修改业务源码、参数、地图或安装产物，没有下发目标及运动指令。

## 已确认的问题

| 项目 | 证据 | 判断 |
| --- | --- | --- |
| 首次目标直接异常 | NX 报 `IsTerrainPathValid requires path`；原测试提前填入空 Path | 我引入的启动回归，先前已修复；本轮没有再次修改 |
| 支撑推断默认开启后收紧通行范围 | 同一冻结地图、两个日志拒绝位置，关闭推断时地面检查通过，开启时都返回 `missing_ground_support` | 新规则不兼容原邻近支撑语义；默认启用前的场景比较不足 |
| 短时输入异常直接取消任务 | 适配器在失去 ready 时立即 pause 并请求取消；行为树另设 5 秒等待 | 等待与取消机制职责不一致；此次取消日志走的是适配器分支 |

支撑规则变化位于 `src/nav2/astar_3d_planner/src/occupy_map.cpp:706`。开启推断时，`findGroundUnlocked` 只查询当前 XY 列的实测或推断地面，失败后直接返回；关闭时仍会搜索周围列。因此这个开关不只是“多补一些地面”，还会取消旧的邻近借用规则。10-26 的实现说明已经记载了这种变化，但当时把它作为默认优化启用，没有充分验证对实际稀疏地图的负面影响。

`src/nav2/astar_3d_planner/src/ground_support.cpp:76` 要求样本在角度上严格包围查询列：最大角度缺口达到 180° 就拒绝。两处日志查询位置的邻居高度范围分别约 0.006 m 和 0.0034 m，但样本分布都恰好落在该几何边界。这里拒绝的原因不是地面实际有坡道，而是观测覆盖不满足新规则。真实平坦与传感器已充分证明平坦是两回事；这不等于应该把所有未知区域放行。

## 查阅上游后的判断

1. [Nav2 Humble 的 IsPathValid 源码](https://github.com/ros-navigation/navigation2/blob/humble/nav2_behavior_tree/plugins/condition/is_path_valid_condition.cpp) 没有把未读取到 path 直接变成该项运行时异常；[Humble 官方行为树](https://github.com/ros-navigation/navigation2/blob/humble/nav2_bt_navigator/behavior_trees/nav_to_pose_with_consistent_replanning_and_if_path_becomes_invalid.xml) 将新目标判断放在路径检查之前。我们的条件顺序和缺值处理都发生了变化，却漏测真实首次启动，这是明确的兼容性遗漏。不是说必须照抄整个上游行为树。
2. [Nav2 官方调参指南](https://github.com/ros-navigation/docs.nav2.org/blob/rolling/docs/configuration_and_development/tuning_guide.md) 说明，连续的障碍代价梯度有助于通道居中，矩形机器人应使用真实几何外廓。它不能修复被地面规则切断的通行区域。该指南是 rolling 的一般设计建议，不将其新版本参数直接套用到 Humble。
3. [Humble Smac 说明](https://github.com/ros-navigation/navigation2/blob/humble/nav2_smac_planner/README.md) 将带朝向的运动模型、碰撞检测、代价和路径平滑一起考虑；[平滑器实现](https://github.com/ros-navigation/navigation2/blob/humble/nav2_smac_planner/src/smoother.cpp) 会检查更新后的可行性。现有“先找支撑路径，再拉直/修角，再做转向扫掠，失败后追加搜索”的组合，并不等同于完整 Hybrid-A*。逐项增加补丁会增加规则相互冲突的机会。

当前全局 costmap 配置使用 `AlwaysCurrentLayer`，自定义规划器另读自己的支撑和障碍地图。因此不能只改插件名就期望 Smac 正确工作；必须先准备真正供它使用的全局代价地图。没有在本轮替换规划器。

## 角速度补偿的边界

补偿在控制输出桥接端，不直接生成 `/plan`，不发布定位 TF，也不负责取消目标。因此它不能直接解释已复现的支撑拒绝或适配器取消分支。

但它可能改变真实转向与跟踪。现有模型主要来自正方向指令与 EKF 速度均值；负方向按用户要求假定对称，没有独立外部角度对照，也没有本次导航的开关对照。不能据拟合均值很好就宣称已排除控制影响。当前模型将 0.35 rad/s 的输入映射到约 0.3347 rad/s，说明它也会减小部分角速度，并非一律增大。

## 建议的保留与处理顺序

| 项目 | 建议 | 完成判断 |
| --- | --- | --- |
| 支撑推断默认策略 | 优先重新评估默认开启；先建立关闭时的冻结输入基线，再单独修正地面表示与查询一致性 | 相同起终点、地图、障碍和姿态下，比较完整规划的成功、长度、转折和矩形扫掠，不只比两个点 |
| 首次启动修复 | 保留已经完成的修复 | 真正未赋值的黑板、首次目标、更新目标均覆盖 |
| 数据失效处理 | 统一停车、等待和取消的职责；保留时效及定位检查 | 短时异常与持续失效分别重现，确认状态转换；恢复前重新验证条件和路线 |
| 碰撞检测和拒绝原因 | 保留，不为提高数字成功率直接放宽 | 对每个误报保留原始回波、来源和实际姿态证据 |
| 角速度补偿 | 下一次受控测试先做开关对照 | 同一姿态与目标，记录请求速度、发送速度、融合里程计及定位状态 |
| 新的平滑或搜索补丁 | 暂停叠加 | 先用完整冻结输入证明现有回归已消除 |

本轮没有证明全部近期修改都应回退，也没有证明修复上述问题后真机必定通过。已证明的是：首次启动漏测、支撑语义变化和取消机制配合不足都需要承担并纠正；不能继续把失败主要归咎于场地或传感器。
