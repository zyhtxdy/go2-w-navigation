# 重定位后台调度改进与验证（2026-10-21）

## 触发问题

此前 NX 容器内只读采样发现：输入点云约 10 Hz、年龄约 0.05 s，但全局配准单轮耗时
3.14～3.35 s，超过原有 3 s 新鲜度门槛，结果被拒绝，没有有效的 map→odom。
原始排查见 [NX 诊断](../2026-10-21-nx-localization-diagnosis/README.md)。

## 改动

1. 后台独立全局搜索；前台按默认 0.2 s 处理间隔，对最新扫描做核验或局部跟踪。两个队列均只保留最新输入。
2. 后台结果只提供初值。根据对应的里程计增量推进全部原有候选，再对新扫描完整配准并重新计算质量、歧义和退化指标；不沿用旧分数、不缩减候选、不重写旧结果时间戳。
3. 三帧不同时间戳的一致确认、原有 3 s 输入/结果新鲜度、3 s 跟踪超时及质量门槛保持。手动重置、无效输入或里程计跳变发生后，通过代次和输入 epoch 拒绝在途旧结果。
4. 已定位时，全局检查间隔 1 s 从后台作业完成时计算，不再由旧扫描时间触发连续占用。局部跟踪可能暂时错配，下一次全局复核前存在检测延迟。
5. 初值最多允许 8 s；最近一次新扫描全局核验超过 8 s 则判失效。这两项约束独立于新扫描 3 s 新鲜度。完整搜索不能无限失联而仅靠局部跟踪维持有效。
6. 新增后台耗时、阶段、初值扫描时间与新扫描核验时间诊断。保留 PCL 原有 GICP 优化器；尝试过的内层优化器未达到预期收益，未纳入最终代码。

## 本机验证

- Release 编译通过。19 个配准测试、12 个运行时测试、2 个实际 ROS 节点测试通过。
- 离线导航的 11 个系统测试、20 个适配器边界测试、28 个导航门控测试通过。
- 测试覆盖新扫描重新打分、重复地点歧义拒绝、全部原候选保留、里程计推进、旧输入拒绝、停止输入失效、搬动后恢复、无 TF/运动发布者等。
- 保存的三帧分别有 27 / 33 / 34 个候选，全部保留。完整搜索约 516 / 620 / 893 ms；同帧暖启动核验约 127 / 244 / 245 ms。见 [基准](benchmark_async_verification.csv)。这是同帧微基准，不代表移动扫描的实际耗时。

### 新鲜度压力回放（另 1 遍，仅测试参数）

独立 domain 119，把输入/结果新鲜度由 3 s 收紧至 0.5 s，其余质量门槛保留。
该配置位于 [freshness_stress.yaml](freshness_stress.yaml)，没有作为部署参数。

- 得到 63 次不同时间戳的有效定位，其中 15 次新扫描全局核验。
- 新扫描核验计算耗时最大 413.5 ms；首条有效诊断相对该新扫描年龄最大约 0.488 s。
- 11 次有效核验使用比新扫描早 0.5 s 以上的初值，证明旧搜索只作初值，新扫描单独通过新鲜度判断。
- 超时核验确实被拒绝，报告出现 `matching_result_stale`；ready 仅约 17.42 s。这证明门槛仍在工作，不代表压力参数可以用于导航。
- 诊断原因按消息条数统计，会重复同一个结果，不能当成独立失败次数。
