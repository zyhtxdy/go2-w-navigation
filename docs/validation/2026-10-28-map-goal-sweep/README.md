## 有没有把平地误判为无地面或坡道

本次已执行请求中，没有记录到单纯因缺少地面支撑、坡度或台阶而规划失败。记录到的首个直线候选拒绝也都是碰撞类原因。这个结论限于本批目标及已记录诊断，不能推广为以后永远不会误判。

44 次普通失败的结构化诊断为：

| 原因 | 次数 |
| --- | --- |
| 终点朝向下车身外廓碰撞 | 26 |
| 路径或旋转扫掠碰撞 | 10 |
| 目标附近候选地面的车体净空被挡 | 8 |

最后 8 次的异常文本写“找不到安全地面”，容易误解成没有支撑。详细诊断实际为 `goal_body_clearance_blocked`：有支撑层，但候选点均被占用检查拒绝。例如目标 `(3.5,0.4)` 的一次失败有 12 个支撑候选，12 个都因车体净空被挡而拒绝。

作为完整矩阵中的一个便于核对的子集，Y=-0.6/-0.1 且目标朝向为 0° 的中间带网格目标，实际执行 23 次、23 次返回有效路径。这只是同一批数据的分类统计，不是另一轮独立试验；其他朝向及位置的失败仍全部保留。

## 碰撞点从哪里来

44 次失败中，28 次诊断引用 `/offline_map/obstacles`。逐点核对原地图的 `hazard_sources.csv`，这些碰撞点都标记为实测来源，没有命中合成危险点。另 16 次引用 `/terrain/obstacles_measured_global` 的实时实测回波。

例如 `(1.5,0.4)` 附近的终点拒绝，会命中固定图点 `(1.1153,0.5954,-0.0600)`；它在所用矩形外廓中。碰撞点有回波来源，不是本轮地面插值新造出来的坡道或障碍，但“实测来源”本身不能独立证明它一定是实体障碍：仍须区分环境物体、反射和配准误差。

前 16 个碰撞事件保留了受限点云窗口。部分对应位置在约 6 秒窗口内有 58～59 帧配准点云回波，说明并非只有一个孤立发布。原始雷达帧没有保存到可用的同戳 map 变换，不能据原始帧的零匹配数声称“原始点云没有这个障碍”。证据存在事件数和内存上限，不覆盖所有失败的原始窗口。

## 门控拦截

53 次普通目标拦截显示 `localization_not_ready:navigation_input_recovery_wait`。对应日志先出现 `global_obstacle_source_stale`，随后等待恢复；该轮等待达到 3 秒后终止。不能把这些目标算作缺地面或碰撞误判。

批量请求、搜索占锁及输入处理调度是否导致障碍更新迟到，本轮尚未单独做因果对照。现有证据只能确认时效保护触发，不能直接归因于网络，也没有通过放宽时效界限掩盖它。
