以下事件时间均按 **NX 日志时间换算为 UTC+8**。一次 SSH 时间对照显示 NX 比笔记本快约 **333.90 秒**，该次往返约 0.46 秒。未修改任一设备时钟。不能把 NX 内部数据的接收戳龄与跨机时差混为一谈。

订阅程序对里程计和 TF 按 40ms 节流，对原始代价地图按 0.5 秒节流，对障碍点云按 1 秒节流；对应的记录数量不能当作真实发布频率。速度命令没有人为节流。

## 明确的控制器求解失败

当前启动会话日志包含以下 **3 次求解异常**，不是 3 个独立目标的成功率：

| NX 日志时间 | 日志及后续 |
| --- | --- |
| 15:00:29.597 | Optimizer fail to compute path；FollowPath ABORTED；清局部地图后重试 |
| 15:01:15.317 | 同一异常；FollowPath ABORTED；清局部地图后重试 |
| 15:01:16.217 | 同一异常；FollowPath ABORTED；随后重新执行 |

按该版本源码和本次实际启用的 critics，CostCritic 将采样轨迹全部判为碰撞后触发失败标记；重试仍失败会抛出该异常。这表示优化器没有找到它认为可行的控制序列，不能断言这些时刻一定持续输出有效运动指令。

失败发生时没有同步记录其内部全部采样轨迹与局部地图，不能再进一步确定是错误障碍、机器人处于被判占用的姿态、可行绕行没有采样到，还是其他几何原因。当前原始日志只有最终失败信息，不足以把原因分到这些分支。

同一份完整控制器日志中有 1971 条 `Control loop missed its desired rate of 20Hz`。这只是日志计数，不是丢包率或规划失败率。第二轮起步转向采样窗口中，控制器输出约 10Hz，平滑器/桥接约 20Hz；第三轮包含任务切换、求解与空档，不能用整段平均频率代表单次 MPPI 计算耗时。

该 Humble 版本的失败重试最终抛 `std::runtime_error`，而 ControllerServer 的 `failure_tolerance` 重试分支只接 `nav2_core::PlannerException`；日志中的这几次因此直接结束当前 FollowPath，随后由上层恢复，不等同于整个 NavigateToPose 目标已经取消。

## 全局路径判定的干扰

第三轮记录在 15:12:58～15:12:59 连续三次 `footprint_collision` 后触发全局重规划，并向运行中的控制器下发新路径。

8 条碰撞诊断里的代表实测点均在被检查矩形外；但全局检查使用 10cm 完整体素方格和最多约 1.25cm 的连续移动采样余量。这足以解释“代表点在外仍判碰撞”的几何结果，不能直接认定为错误朝向或重复膨胀。其中 7 条已超出近起点实测范围精化半径 0.8m。

代表点不等于体素内所有点，因此不能认定这 8 次全为误报。能确认的是全局保守判定与重规划在干扰本次路径跟踪；不能把它直接等同于 MPPI 对真实障碍不避让。

## 尚未证实的动态避障原因

`CostCritic.near_goal_distance=1.0m` 在该版本会关闭普通软障碍代价，硬碰撞仍保留；该距离参照裁剪后的 MPPI 路径末端，未必是 RViz 最终目标。这是后续需要与真实障碍事件对照的机制，不是本次已经证实的根因。

本次检查确认：碰撞检测配置已生效、实时输入存在、速度桥接在工作，同时确有优化器失败、控制周期超时和全局重规划。**未复现并锁定“实际障碍进入路径但 MPPI 不绕行”的因果链。** 下次应在同一个障碍事件内同步保留局部地图、实际路径、机器人姿态、控制输出与求解失败信息，再决定是感知/几何误判、搜索采样不足还是控制执行问题。
