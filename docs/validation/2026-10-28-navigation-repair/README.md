# 2026-10-28 导航支撑判定与恢复逻辑修正

本轮仅在本机修改、编译和运行隔离的软件测试。没有 SSH 连接 NX，没有同步或编译 NX，没有启动机器人驱动、运动桥接或发送真实导航目标。软件测试使用本机独立 ROS 域和 localhost，产生的控制消息只交给测试观察器。

## 修改结果

1. 共享导航参数中的 `GridBased.support_inference_enabled` 恢复为默认 `false`。这恢复原邻近支撑判断；严格推断仍可明确选择开启，其原有拒绝未知区域规则没有被偷偷放宽。没有修改保存地图、固定障碍、矩形外廓或角速度补偿。
2. 离线适配器对明确的缺失/过期原因立即发送零速，最多等待 3 s（稳态时钟）恢复。初次启动、时钟回退、地图或坐标系异常、歧义定位等不走该恢复分支；持续异常仍按原有取消流程处理。
3. 恢复必须同时满足：全部原有数据时效检查通过、map→odom 相对停车前没有超过原修正界限、针对当前 `/plan` 的独立详细路径验证请求成功。等待期间的速度直接丢弃，不缓存重放。只有之后收到的新命令才可能通过。
4. 路径被替换、再次断流、验证 RPC 超时或失败时，旧结果不能放行。变化的异常原因和重复心跳不会重新起算 3 s 截止时间。严重错误中断等待并取消；已经进入取消流程的任务仍须完成取消，不能被数据恢复绕过。
5. 将规划就绪与运动就绪分开：`/offline_localization/planning_ready` 供规划器计算和复核；`/offline_localization/ready` 继续表示最终运动门控。离线启动参数自动指定前者，避免“必须先允许速度才能复核路径”的循环等待。独立规划器默认保留旧话题，兼容已有入口。在线模式不使用离线恢复门控。

3 s 是本次软件恢复策略的等待界限，不是测得的 NX 恢复时间，不保证所有超时都能自行恢复。等待必须包含数据重新确认及路径验证，超过后取消任务，需要重新下发目标。

总计 505 项软件检查。数量不是导航质量的替代证据；本轮补充的重点包括：

- 真实首次目标尚未赋值的路径黑板检查继续通过。
- 短时缺失时保留父任务，门控保持零速，数据恢复后必须收到当前路径的验证结果。
- 完成但尚未消费的旧验证遇到第二次断流也会作废。
- 路径替换、真实碰撞、验证服务缺失、RPC 异常与超时均不能放行。
- 恢复超时、错误原因改变、定位跳变、时钟回退不会绕过取消保护。
- 真实 ROS 适配器进程、假取消及验证服务的集成场景通过，过程未发布任何 Go2 API 请求。
- 公开规划器在最终速度门控为 false 时，能经单独的 planning_ready 完成详细路径复核，验证没有门控死锁。
- 实时障碍仍引起绕行，未来时间戳不能清掉当前障碍，近身矩形角碰撞仍拒绝路径。

首轮完整 Python 检查发现一个旧断言要求 0.48 m 参数必须产生超过 0.4 m 的侧向绕行；完整矩形模式下该参数已用于软代价，硬碰撞由真实矩形决定。该断言改为基于车身宽度的避让检查，保留两种参数下的实时障碍、清除、错误时间戳和近身矩形反例。没有为了通过测试修改机器人外廓或碰撞代码。

结果记录：`all_checks.log`、`test_counts.json`。`installed_checks.json` 确认本机安装的适配器、取消保护、共享参数生成器、离线参数文件和规划器动态库与本轮源码/构建产物一致。

## 边界与后续真机检查

软件结果不能证明角速度补偿、实际执行误差、无线网络和 NX 的核验调度已正常。这些本轮没有真机对照。实际执行中发生不满足白名单的定位失效，或者等待超过 3 s，仍会取消；这不是取消保护被移除。

首次真机复测应区分三个量：规划出的路径形状、实际控制请求与里程计响应、定位和障碍健康状态。先用相同目标比较路径，再记录执行，避免同时改变补偿和规划参数。

本轮没有同步 NX。文件改动和构建信息以本目录的源码差异、哈希及日志为准。
