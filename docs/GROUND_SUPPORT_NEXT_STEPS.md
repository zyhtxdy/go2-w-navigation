# 地面支撑不足的处理顺序

2026-11-10 更新：近处障碍缺失与地面支撑稀疏需要分开检查。只读快照中，
机器人侧前方约 0.5～0.65 m 有真实竖直回波，但未进入 `/terrain/obstacles`；
共线栅格缺少二维地面拟合条件时，原分类会跳过这些回波。已在本机增加近场
实测竖向结构识别，标准 Go2W 配置启用。后续已将它接入局部障碍与全局实时
障碍流，不生成支撑面，不修改保存的离线地图或地图导出时的地形分类。

相关参数在 `terrain_costmap.yaml`：`near_obstacle_*` 限定当前帧的 0.4～1.2 m
范围、相对 base_link 的 -0.35～0.40 m 高度与自体矩形。独立体素、至少两个
实测低层返回及三个上层候选组成的空间簇用于过滤孤立噪声。低层只是实测
高度参照，不代表已确认地面；雷达没扫到的物体仍无法识别。

`/terrain/clear_scan` 改为只用当前实际回波生成有限清线，止于最近回波或已分类
障碍前 `clearing_endpoint_margin=0.10 m`，缺测方向输出 NaN。两套 Nav2 配置
的 `terrain_clear.inf_is_valid` 均为 false。这样不会把无回波方向直接清到 8 m；
代价是障碍移开后，要再次看到更远的真实回波才能清除原有标记，盲区中的旧
标记可能保留。近障碍检测只使用当前帧；检测结果按真实 XYZ 转到 odom，全局
实测流沿用 0.6 秒原始观测时间期限。短时缺测不立即丢失证据，过期或录包时间
回退后清除，不把旧检测伪装成新回波。在线 mixed 全局流仍需两帧确认。

## 平整实验室：先补真实覆盖，再验证规划

使用既有建图入口。规划端禁用运动桥，仅检查规划结果：

```bash
ros2 launch navigation_bringup real_nav2.launch.py start_cmd_vel_bridge:=false
```

需关闭本人已有的速度桥接进程，避免另一份桥接仍消费导航速度。此选项不会影响其他人的程序，也不会替操作者关闭其他人的控制。

由操作者遥控采集场地，使起点和计划路线的地面从其他位置被雷达真实扫描到。规划器需要在采集期间运行，才能累计 `/terrain/support`。回到已覆盖的起点，再在 RViz 指定已覆盖的目标，先检查：

- 起点附近有正确高度的地面支撑。
- 目标附近有地面支撑，而非桌面等高层支撑。
- 起点至目标的地面连续，规划日志没有安全地面缺失或不连通错误。
- 路线满足机器人包络与障碍净空检查。

这是一种现场覆盖验证方法，没有记录证明遥控一圈必然解决。当前地形只合并短时间窗口；先建完图再启动规划器，不会自动把旧的完整地面图加载进去。

## 已建地图与隧道阶段

长期需要地面支撑图的保存、加载与坐标对齐，使已知地图导航能使用先前真实观测过的地面；当前这条链路没有完整的支撑图加载功能。

首次进入未知隧道仍需改善近场观测。先核实 XT16 实际高度、扫描朝向和机身遮挡；可评估调整安装或接入现有机载近场雷达。新传感器接入需核对坐标系、时间戳和实测覆盖；移动 XT16 后需重新标定外参。

不直接放大起点投影半径来跨过约 2 m 未观测区域：当前起点桥接主要检查障碍净空，尚不能证明桥段有连续地面。`point_filter_num` 减少抽稀仅能提高已有回波密度，不能解决视场之外的缺口。

运动建图漂移仍需独立检查。修正地面规划与改善覆盖，不等于解决 FAST-LIO 的运动漂移。
